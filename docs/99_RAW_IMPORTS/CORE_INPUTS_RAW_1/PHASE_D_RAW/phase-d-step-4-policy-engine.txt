1. PHASE IDENTITY LAYER
	1.1 Phase Name

		Phase D — Step 4: Policy Engine (Execution Governance Layer)

	1.2 Phase Role

		Deterministic governance enforcement layer that:

			consumes RiskApprovedIntent
			applies policy + governance rules (non-risk)
			controls execution behavior (timing, pacing, permissions)
			produces PolicyDecisionIntent

	1.3 Phase Objective

		Transform:

			RiskApprovedIntent → PolicyDecisionIntent

		Such that:

			all intents are policy-compliant
			execution behavior is controlled + governed
			no economic meaning is altered
			output remains deterministic and replay-safe

	1.4 Why This Phase Exists

		Prevents:

			(F1) policy violations despite risk approval
			(F2) over-trading / execution bursts
			(F3) regulatory breaches
			(F4) strategy misuse (disabled / restricted strategies executing)
			(F5) uncontrolled execution pacing

		Risk-safe ≠ Policy-safe
		This phase enforces institutional governance

5. LOGIC / RULE ENGINE
	5.1 Rule Classes

		R1 — Input Validation
		R2 — Policy Rule Binding
		R3 — Time Window Validation
		R4 — Permission Validation
		R5 — Behavioral Control (frequency/cooldown)
		R6 — Pacing / Modification
		R7 — Policy Decision Assignment
		R8 — Output Construction

	5.2 Policy Rule Types

	A. HARD POLICY (REJECT)
		trading outside allowed hours
		banned instrument
		disabled strategy
		regulatory violation

	B. SOFT POLICY (MODIFY)
		max trades per interval
		cooldown enforcement
		execution pacing
		size caps (STRICT upper bound)

		Deterministic Frequency Evaluation Rule:

			trade_count_window MUST be computed using:

				event_time-based fixed window

			ordering_key = {
				event_time ASC
				sequence_id ASC
			}

			Constraint:

				evaluation MUST follow deterministic ordered stream

	5.3 Decision Logic
		IF any HARD policy violated:
			status = REJECT

		ELSE:
			apply MODIFY rules

			IF modifications applied:
				status = MODIFY
			ELSE:
				status = ALLOW

	5.4 Modification Rules (STRICT)

		Allowed modifications ONLY:

		allowed_modifications = {
			execution_delay
			execution_batching
			size_cap (≤ approved_size only)
			slicing_instruction
		}

		Forbidden:

			instrument change
			direction change
			intent creation

		Zero-Size Enforcement Rule (MANDATORY):

			IF modified_size == 0:

				status = REJECT

				policy_flag = ZERO_SIZE_REJECTION

		Policy Modification Constraint (MANDATORY)

			Policy Engine MAY reduce size ONLY under:

				execution-behavior control (NOT risk override)

			Conditions:

				1. approved_size MUST NOT be exceeded
				2. reduction MUST NOT violate:
					- risk constraints
					- portfolio constraints
				3. reduction MUST NOT change:
					- direction
					- instrument
					- intent classification

			Classification:

				size reduction = execution shaping
				NOT economic mutation

			STRICT PROHIBITIONS:

				Policy Engine MUST NOT:

					increase size
					override risk decisions
					bypass constraint_output

			Violation → PHASE INVALID

	5.5 Rule Execution Order (MANDATORY)
		1. Input Validation
		2. Policy Rule Binding
		3. HARD Policy Evaluation
		4. Behavioral Controls
		5. Modification Rules
		6. Decision Assignment
		7. Output Construction

		Constraint:

			higher precedence rules dominate
			no override allowed

		Policy Precedence Tie-Break Rule (MANDATORY):

			IF multiple PolicyRules share same precedence_level:

				apply deterministic ordering:

					1. policy_type priority (fixed global map)
					2. policy_id ASC (lexicographic)

			Constraint:

				identical rule set → identical evaluation order

			Violation:
				→ NON-DETERMINISTIC POLICY ENGINE

		Sequential Policy Evaluation Rule (MANDATORY):

			All intents MUST be processed in strict order:

			ordering_key = {
				event_time ASC
				origin_type ASC
				sequence_id ASC
			}

			FOR each intent:

				evaluate policy using PolicyState_current

				produce PolicyDecisionIntent

				update PolicyState_current using PolicyStateTransition

		State Update MUST occur IMMEDIATELY after each intent evaluation
			and BEFORE next intent evaluation

9. STATE & DATA MODEL

	State Model (CONTROLLED STATE — NOT EXTERNAL)

		PolicyStateSnapshot = {
			trade_count_window
			last_execution_time_per_instrument
			cooldown_tracker
		}

	PolicyStateTransition (MANDATORY):

		Define deterministic state evolution:

		PolicyStateTransition (MANDATORY — FULLY DEFINED):

			FOR each processed PolicyDecisionIntent:

				IF policy_status ∈ {ALLOW, MODIFY}:

					trade_count_window = update_window(
						trade_count_window,
						event_time
					)

					last_execution_time_per_instrument[instrument] = event_time

					cooldown_tracker[instrument] = event_time + cooldown_duration

				ELSE IF policy_status == REJECT:

					NO state update

			update_window RULE (MANDATORY):

				trade_count_window MUST:

					- include only events within:
						[event_time - window_size, event_time]

					- be computed using event_time ONLY

					- be strictly deterministic

			cooldown_tracker RULE:

				cooldown_active IF:

					event_time < cooldown_tracker[instrument]

			CONSTRAINTS:

				- ALL updates MUST use event_time (NOT system time)
				- ALL updates MUST be deterministic
				- NO partial updates allowed

		assert state_update_time_source == event_time
			assert no system_clock usage
