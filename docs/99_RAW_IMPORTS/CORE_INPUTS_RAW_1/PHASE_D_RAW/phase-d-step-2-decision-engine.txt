PHASE D — STEP 2: DECISION ENGINE (EXECUTION LAYER)
1. PHASE IDENTITY LAYER
	1.1 Phase Name

		Phase D — Step 2: Decision Engine (Execution Validation Layer)

	1.2 Phase Role

		Deterministic execution-side validation and normalization layer that:

			consumes execution_intent_stream (from Step 1)
			validates execution readiness
			resolves conflicts deterministically
			guarantees ordering and consistency
			produces decision_validated_intent_stream

		This sits strictly before Risk Engine per Phase D macro ordering

	1.3 Phase Objective

		Transform:

			ExecutionIntent → DecisionValidatedIntent

		Such that output is:

			conflict-free
			schema-complete
			deterministically ordered
			execution-safe (structurally only, NOT risk-safe)

	1.4 Why This Phase Exists

		Prevents:

			(F1) conflicting execution intents entering Risk Engine
			(F2) duplicate trades causing double exposure
			(F3) non-deterministic ordering → execution divergence
			(F4) malformed intents causing downstream failure
			(F5) ambiguous intent sets (same instrument, opposing directions)

	4.6 ConflictGroup Definition (MANDATORY)

			conflict_group_id = HASH_v1(
				sorted(
					execution_intent_id[]
				)
			)

			grouping_key = {
				instrument
			}

			Rules:

			- All intents sharing same instrument MUST belong to same ConflictGroup
			- ConflictGraph MUST be constructed per instrument
			- grouping MUST be deterministic and complete

			Constraint:

			same execution_intent_stream → identical ConflictGroups

			sorted_execution_intent_ids MUST be ordered by:

					execution_intent_id ASC (lexicographic)

				Constraint:

				- sorting method MUST be fixed and versioned
				- identical input → identical sorted list

5. LOGIC / RULE ENGINE
	5.1 Rule Classes

		R1 — Schema Validation
		R2 — Consistency Validation
		R3 — Conflict Detection
		R4 — Deduplication
		R5 — Conflict Graph Resolution (includes priority ordering)
		R6 — Ordering Enforcement
		R7 — Sequencing Assignment

	5.2 Validation Rules

		Reject intent if:

			missing required fields
			invalid enum values
			target_size ≤ 0
			duplicate execution_intent_id (pre-resolution)

		R-LINEAGE-CHECK:

			assert current_lineage_hash ==
				   HASH(previous_lineage_hash + current_entity_id)

	5.3 Conflict Detection Rules

		Conflict if:

			same instrument AND opposite direction
			same trade_intent_id duplicated
			overlapping execution scope

	5.4 Deduplication Rule

		If identical intents:

			same {
				trade_intent_id,
				instrument,
				direction,
				target_size
			}

			→ keep ONE (lowest hash)

		dedup_hash = HASH_v1(
				trade_intent_id +
				instrument +
				direction +
				target_size +
				strategy_id
			)

			Rule:

			- duplicates = identical dedup_hash
			- retain lowest execution_intent_id


	5.6 Rule Execution Order (STRICT)
			Schema Validation
			Consistency Validation
			Conflict Grouping
			Deduplication
			Conflict Graph Resolution
			Ordering Enforcement
			Sequencing Assignment
			Output Construction

			No lower rule overrides higher rule

	5.7 Conflict Graph Resolution (MANDATORY)

			Model:

			ConflictGraph = {
				nodes: ExecutionIntent
				edges: conflict_relation
			}

			Conflict Relation:

			- opposite direction
			- overlapping scope

			Resolution Algorithm:

			1. sort nodes by:
			   priority_level DESC
			   event_time ASC
			   origin_type ASC (CORE first)
			   trade_intent_id ASC

			2. iterate sorted list:

			   IF node not eliminated:
				   select node
				   eliminate all conflicting neighbors

			3. output selected set

			Constraint:

			- graph MUST be acyclic post-resolution
			- identical graph → identical output

		Origin Priority Rule (MANDATORY)

			CORE intents MUST dominate EXTERNAL intents in conflict resolution.

			Implementation:

			origin_type priority:
			CORE = 1
			EXTERNAL = 2

			Applied BEFORE trade_intent_id ordering

		overlapping scope MUST be defined as:

			scope_key = {
				instrument
			}

			Constraint:

			- two intents overlap ONLY IF:
				instrument is identical

			No other dimensions allowed

		Priority is applied ONLY inside graph resolution sorting phase.

		No separate priority resolution stage exists.

			1. event_time ASC
			2. origin_type (CORE=1, EXTERNAL=2)
			3. trade_intent_id ASC

		Final Tie-Break Rule (MANDATORY)

			ordering_key = {
				event_time ASC
				origin_type ASC (CORE=1, EXTERNAL=2)
				priority_level DESC
				trade_intent_id ASC
				execution_intent_id ASC
			}

			Constraint:

			- sequence_id MUST be globally unique
			- MUST be stable across replay

		sequence_id assignment MUST occur AFTER:

			- validation
			- deduplication
			- conflict graph resolution (final set)

			Constraint:

			- sequence_id applies ONLY to surviving DecisionValidatedIntent
			- eliminated intents MUST NOT receive sequence_id
