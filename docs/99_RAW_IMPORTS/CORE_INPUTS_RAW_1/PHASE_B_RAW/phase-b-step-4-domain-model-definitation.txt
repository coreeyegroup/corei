PHASE B — STEP 4: DOMAIN MODEL DEFINITION

1. PHASE IDENTITY LAYER
	1.1 Phase Name

		Phase B — Step 4: Domain Model Definition

	1.2 Phase Role

		Defines the complete, deterministic domain model for the constraint system governing all upstream logical outputs from Phase A.

	1.3 Phase Objective

		Construct a fully deterministic, canonical, and execution-safe constraint domain model that formalizes all entities, attributes, relationships, and ownership required for constraint evaluation and enforcement.

	1.4 Why This Phase Exists

		Prevents:

			implicit constraint interpretation
			cross-phase data leakage
			undefined constraint inputs to Phase D
			non-deterministic constraint evaluation behavior
			structural ambiguity in constraint system

		Ensures:

			all constraint logic (Step 5) operates on a closed, canonical domain
			Phase D receives fully defined constraint output objects

4. DOMAIN MODEL DEFINITION (CORE SECTION)
	Canonical Derivation Rule (MANDATORY)

		ALL entities (E1–E10) MUST be constructed ONLY from:

			canonical_input_set

		Constraint:

			No entity may be instantiated from:
				- external inputs
				- intermediate state
				- inferred values

		Violation → INVALID DOMAIN MODEL

	4.1 CORE ENTITIES (MANDATORY — COMPLETE SET)
		E1: Constraint Context

			Deterministic evaluation container for all constraint computation

			Numeric Model Enforcement (MANDATORY)

				ALL numeric values in this phase MUST use:

					fixed-point representation:

						value = integer / 10^6

				Applies to:

					constraint_score
					size_adjustment
					parameter values (min, max, default)
					trigger_value
					threshold_value
					any derived numeric field

				Constraints:

					floating-point arithmetic is strictly forbidden

					ALL computations MUST use deterministic rounding:

						ROUND_HALF_UP

					overflow condition:

						if value exceeds bounds → computation MUST fail

					underflow condition:

						if value < minimum precision → treat as zero

		E2: Constraint Input Snapshot

			Canonical representation of all upstream inputs used for constraint evaluation

		E3: Constraint Rule Definition

			Formal definition of constraint rules (non-executable structure only)

			target_binding_reference = {

					target_entity
					target_field
				}

		E4: Constraint Evaluation Unit

			Per-instrument / per-strategy constraint evaluation object

		E5: Constraint Decision

			Final constraint outcome applied to a trade intent

		E6: Constraint Parameter Set

			All bounded numeric parameters used by constraints

		E7: Constraint Violation Record

			Explicit record of any constraint breach

		E8: Constraint Priority Layer

			Defines precedence hierarchy across constraint types

		E9: Constraint Scope Unit

			Defines scope of constraint application

			Values:

				firm
				portfolio
				strategy
				instrument
				trade

		E10: Constraint Output Object

		Final structured output passed to Phase D


		entity_version_id
			entity_hash

			Constraint:

				entity_hash = HASH_v1(entity_payload)

				entity_version_id MUST be version-controlled

				identical entity definition → identical hash

			Entity Payload Definition Rule (MANDATORY)

				entity_payload MUST include:

					1. entity_id
					2. entity_type
					3. all attributes (ordered)
					4. version_identifiers

				Serialization MUST follow canonical ordering:

					1. entity_type
					2. entity_id
					3. attributes (lexicographic)
					4. version_identifiers

				Constraint:

					identical entity → identical entity_hash

			Hash Construction Rule (MANDATORY)

				All hashes MUST be computed as:

					HASH_v1(canonical_payload)

						- deterministically serialized
						- fixed field order
						- no optional field omission
						- no whitespace variation

				Field ordering MUST follow:

					1. version_identifiers
					2. input_data_snapshot
					3. configuration_snapshot

				Constraint:

					identical canonical_input_set → identical hash

			Output Hash Payload Rule (MANDATORY)

				output_hash MUST include:

					1. version_identifiers
					2. input_data_snapshot
					3. configuration_snapshot
					4. constraint_decision_set (ordered)
					5. violation_set (ordered)

				Constraint:

					output_hash MUST reflect FULL output payload

					decision_time usage → FORBIDDEN
