1. PURPOSE

The COREI Reference System defines the authoritative
institutional framework for preserving and exposing
stable factual knowledge required to understand,
navigate,
interpret,
operate,
implement,
validate,
and continue the COREI institutional system.

Its purpose is to provide a governed location for
information that is primarily used for

lookup,

navigation,

cross-reference,

interpretation,

mapping,

enumeration,

discovery,

and contextual orientation.

The Reference System SHALL make important
institutional facts discoverable without forcing
engineers,
operators,
teams,
automation systems,
or artificial intelligence systems

to reconstruct them from

source code,

chat history,

historical documents,

tribal knowledge,

or scattered implementation artifacts.

Reference SHALL answer questions such as

What is this?

Where is it?

What is its identifier?

What does this code mean?

What depends on what?

Which document is authoritative?

Which Stage contains this work?

Which Phase follows this Phase?

Which service owns this capability?

Which event belongs to which domain?

Which repository path contains this artifact?

Which environment does this identifier represent?

Which broker,
account,
strategy,
portfolio,
market,
currency,
or region

does this identifier refer to?

Reference SHALL preserve discoverability.

It SHALL not replace the authoritative source that
owns the underlying truth.

3. CORE PRINCIPLE

Reference SHALL make institutional truth easier to
find.

Reference SHALL not silently become a second
competing source of truth.

The authoritative owner of a fact SHALL remain
explicit.

Reference material SHALL

point,

map,

index,

summarize,

or enumerate

authoritative facts without creating uncontrolled
duplication.

4. REFERENCE DEFINITION

Reference is structured institutional information
designed primarily for repeated lookup and
orientation.

Reference is usually

stable,

concise,

indexed,

cross-linked,

and discoverable.

5. REFERENCE SYSTEM DEFINITION

The Reference System is the governed collection of

indexes,

registries,

catalogs,

dictionaries,

glossaries,

maps,

matrices,

inventories,

code lists,

identifier references,

dependency references,

and cross-reference artifacts

used to navigate COREI.

6. REFERENCE IS NOT AUTHORITY BY DEFAULT

A reference artifact SHALL not automatically become
the authoritative owner of the fact it describes.

Authority SHALL remain with the designated source
of truth unless explicitly transferred.

7. AUTHORITATIVE REFERENCE

Some reference artifacts MAY themselves be
authoritative.

Examples include

canonical identifier registries,

approved code registries,

official Stage indexes,

or controlled asset registries.

Their authority SHALL be explicit.

8. DERIVED REFERENCE

Derived Reference is generated from another
authoritative source.

Derived reference SHALL identify its source where
required.

9. STATIC REFERENCE

Static Reference changes infrequently and is
maintained through controlled change.

Examples MAY include

domain codes,

document classes,

or constitutional terminology.

10. DYNAMIC REFERENCE

Dynamic Reference changes as the platform evolves.

Examples MAY include

service inventories,

deployment inventories,

active broker registries,

or environment maps.

Dynamic reference SHALL have freshness controls.

12. REFERENCE IDENTITY

Every material reference object SHOULD have a
stable identity.

Identity SHALL be distinct from display name where
necessary.

13. CANONICAL IDENTIFIER

A Canonical Identifier is the approved stable
identifier for a reference object.

Canonical identifiers SHALL not be reused for a
different meaning.

14. DISPLAY NAME

A Display Name is the human-readable name of a
reference object.

Display names MAY change.

Canonical identity SHOULD remain stable.

15. ALIAS

An Alias is an alternate known name for a reference
object.

Aliases SHALL resolve to the canonical identity.

16. LEGACY IDENTIFIER

A Legacy Identifier is a previously used identifier
retained for compatibility,
history,
or migration.

Legacy identifiers SHALL not create identity
ambiguity.

17. REFERENCE CODE

A Reference Code is a controlled compact
representation of a reference object or class.

Examples include

ID

GV

AR

EN

ST

SP

OP

IM

RF.

Codes SHALL have one authoritative meaning within
their defined namespace.

18. NAMESPACE

A Namespace defines the boundary within which an
identifier or code is unique.

Namespaces SHALL be explicit where collisions are
possible.

19. REFERENCE CLASSIFICATION

21. REFERENCE OWNER

22. REFERENCE AUTHORITY

23. SOURCE OF TRUTH POINTER

A reference entry SHOULD identify the authoritative
source of truth where the reference itself is not
authoritative.

24. REFERENCE LINEAGE

Derived reference SHOULD preserve lineage to its
source.

Lineage MAY include

document,

repository,

API,

database,

runtime,

or generated source.

25. REFERENCE FRESHNESS

Reference whose underlying truth changes over time
SHALL expose sufficient freshness information.

Freshness MAY include

version,

generation time,

effective time,

or source baseline.

26. REFERENCE VERSION

Material reference artifacts SHOULD be versioned
where change affects interpretation or
compatibility.

27. REFERENCE EFFECTIVE TIME

A reference entry MAY define when it becomes
effective.

Historical reference MAY preserve previous
effective states.

28. REFERENCE RETIREMENT

Retired reference objects SHALL remain discoverable
where required for

history,

migration,

audit,

or compatibility.

29. REFERENCE TOMBSTONE

A retired reference object MAY retain a tombstone

previous identity,

retirement status,

replacement,

and historical source.

30. REFERENCE INDEX

A Reference Index provides ordered navigation to a
set of reference objects.

Indexes SHALL optimize discovery.

31. REFERENCE REGISTRY

A Reference Registry maintains controlled
identities and attributes for a defined class of
objects.

Registries MAY be authoritative.

32. REFERENCE CATALOG

A Reference Catalog provides discoverable metadata
about available institutional objects.

A catalog MAY aggregate multiple authoritative
sources.

33. REFERENCE INVENTORY

A Reference Inventory identifies what currently
exists within a defined boundary.

Inventories SHOULD expose freshness.

34. REFERENCE DICTIONARY

A Reference Dictionary maps controlled terms,
codes,
or identifiers

to their meanings.

35. GLOSSARY

A Glossary defines institutional terminology.

Glossary definitions SHALL not conflict with
constitutional definitions.

36. TAXONOMY

A Taxonomy classifies institutional concepts into
controlled categories.

37. ONTOLOGY

An Ontology defines formal relationships between
institutional concepts where required.

Ontology SHALL not be introduced where a simpler
controlled model is sufficient.

38. REFERENCE MAP

A Reference Map shows relationships between
reference objects.

Examples include

Stage to Phase,

Domain to Service,

Service to Repository,

Event to Schema,

Broker to Account,

Strategy to Portfolio.

39. CROSS-REFERENCE

A Cross-Reference links related institutional
objects across boundaries.

40. REFERENCE MATRIX

A Reference Matrix compares or maps multiple
dimensions.

Examples include

Stage × Phase

Environment × Deployment

Broker × Account

Strategy × Portfolio

Role × Permission.

41. REFERENCE GRAPH

A Reference Graph represents connected objects and
relationships.

Graphs MAY support

dependency discovery,

impact analysis,

lineage,

and navigation.

42. REFERENCE RESOLUTION

Reference Resolution is the process of converting a

name,

alias,

code,

or identifier

into the canonical reference object.

43. AMBIGUOUS REFERENCE

Ambiguous references SHALL be resolved before
critical use.

A name that maps to multiple objects SHALL not be
silently interpreted.

44. UNKNOWN REFERENCE

Unknown reference values SHALL remain explicit.

UNKNOWN SHALL not be silently converted into a
guessed identity.

45. REFERENCE VALIDATION

Reference validation SHALL verify

identity,

format,

uniqueness,

source,

status,

and relationships

where applicable.

46. REFERENCE INTEGRITY

Reference integrity requires that

identifiers resolve correctly,

relationships are valid,

deprecated entries remain traceable,

and conflicting meanings are prevented.

47. REFERENCE CONSISTENCY

The same canonical reference object SHALL have
consistent meaning across COREI.

48. REFERENCE DUPLICATION

Duplicate reference representations MAY exist for
performance or convenience.

The authoritative relationship SHALL remain
explicit.

49. REFERENCE DRIFT

Reference Drift occurs when a reference artifact no
longer matches the authoritative underlying state.

Drift SHALL be detected and reconciled.

50. REFERENCE CONFLICT

When reference sources conflict,
the authoritative source hierarchy SHALL determine
resolution.

Conflict SHALL not be silently hidden.

130. AI SHALL NOT TREAT SUMMARY AS SOURCE

AI SHALL not treat a reference summary as more
authoritative than the source it references.

131. AI SHALL NOT INVENT IDENTIFIERS

Canonical identifiers SHALL not be invented when an
authoritative registry exists.

132. AI SHALL NOT GUESS AMBIGUOUS REFERENCES

Ambiguous references SHALL be resolved explicitly
before critical action.

133. AI SHALL PRESERVE CANONICAL NAMES

Where canonical names and identifiers exist,
AI SHALL preserve them in implementation and
documentation.

134. AI SHALL PRESERVE FILE PATHS

Where repository files are referenced,
AI SHALL preserve exact authoritative paths.

135. AI SHALL PRESERVE STAGE AND PHASE IDENTITY

AI SHALL not renumber,
reorder,
or reinterpret

approved Stage and Phase identities without
explicit authority.

136. AI SHALL PRESERVE DOMAIN IDENTITY

AI SHALL not silently redefine domain names,
codes,
or ownership.

137. AI SHALL IDENTIFY REFERENCE CONFLICT

When reference artifacts conflict,
AI SHALL identify the conflict and determine the
higher authority source.

138. AI SHALL IDENTIFY STALE REFERENCE

AI SHOULD identify when dynamic reference appears
stale relative to authoritative current state.

139. AI SHALL NOT REBUILD REFERENCE BY MEMORY

Where authoritative reference exists,
AI SHALL use it rather than reconstructing project
facts from conversation memory.

140. NO UNCONTROLLED REFERENCE DUPLICATION

Reference SHALL not create competing truth through
unmanaged copies.

141. NO IDENTIFIER REUSE

A canonical identifier SHALL not be reassigned to a
different institutional meaning.

142. NO SILENT ALIAS COLLISION

Aliases that resolve to multiple objects SHALL be
treated as ambiguous.

143. NO UNKNOWN SOURCE

Material derived reference SHOULD identify its
authoritative source.

144. NO STALE DYNAMIC REFERENCE WITHOUT SIGNAL

Dynamic reference SHALL not appear current when its
freshness is unknown.

145. NO SECRET VALUES IN GENERAL REFERENCE

passwords,

private keys,

tokens,

or protected secret values.

146. NO REFERENCE BY CHAT ALONE

Critical institutional reference SHALL not exist
solely in conversation history.

147. NO REFERENCE BY HUMAN MEMORY ALONE

Critical identity and mapping information SHALL be
persisted.

148. NO SILENT REFERENCE DRIFT

Reference drift SHALL be detected and reconciled.

149. NO REFERENCE WITHOUT OWNERSHIP

Material reference collections SHALL have an owner.

150. NO REFERENCE WITHOUT LIFECYCLE

Reference entries SHALL support controlled

creation,

change,

deprecation,

and retirement

where applicable.

151. NO REFERENCE OVERRIDE OF ARCHITECTURE

Reference SHALL describe approved architecture.

It SHALL not redesign architecture.

152. NO REFERENCE OVERRIDE OF IMPLEMENTATION

Reference SHALL not claim implementation exists
when the repository or runtime proves otherwise.

153. NO REFERENCE OVERRIDE OF OPERATIONS

Reference SHALL not claim a system is operational
when actual operational state proves otherwise.

154. NO REFERENCE OVERRIDE OF TRADING STATE

Reference SHALL not be treated as the source of
truth for live

orders,

fills,

positions,

capital,

or risk

unless explicitly designed and authorized for that
purpose.
