1. PURPOSE

The COREI Implementation Overview defines the
authoritative institutional model for translating
approved

identity,

governance,

architecture,

engineering,

standards,

specifications,

and operational requirements

into working production capability.

Its purpose is to ensure that implementation is

controlled,

deterministic,

architecture-faithful,

repository-grounded,

dependency-aware,

validation-driven,

operationally realistic,

and institutionally traceable.

Implementation SHALL realize approved design.

Implementation SHALL NOT silently redefine it.

2. SCOPE

This document governs implementation across

infrastructure,

platforms,

services,

applications,

data systems,

security systems,

identity systems,

trading systems,

risk systems,

portfolio systems,

execution systems,

operator environments,

automation,

artificial intelligence systems,

and future institutional capability.

It governs

implementation authority,

repository use,

source-of-truth hierarchy,

stage execution,

phase execution,

step execution,

subsystem ownership,

dependency order,

file creation,

file modification,

integration,

validation,

documentation,

migration,

activation,

and completion.

No implementation step SHALL bypass required
authority or validation.

4. IMPLEMENTATION IS EXECUTION

Implementation is the controlled realization of
approved institutional design.

Implementation SHALL NOT become

unbounded brainstorming,

architecture replacement,

unapproved redesign,

experimental patch work,

or undocumented mutation.

Where architecture is approved,
implementation SHALL consume it.

5. AUTHORITATIVE SOURCE HIERARCHY

Implementation SHALL follow the authoritative
source hierarchy.

The hierarchy SHALL include, according to project
context,

COREI Constitutional Authority

↓

COREI Governance

↓

Approved Architecture

↓

Approved Engineering Model

↓

Approved Standards

↓

Approved Specifications

↓

Approved Operations Model

↓

Approved Stage and Phase Documents

↓

Repository State

↓

Implementation Evidence

Conflicts SHALL be resolved according to authority,
not convenience.

6. REPOSITORY AS IMPLEMENTATION TRUTH

The repository SHALL be the authoritative source of
implemented system state.

Documentation defines intended authority and
design.

The repository defines what currently exists.

Implementation decisions SHALL inspect repository
reality before modifying the system.

7. DOCUMENTATION AS DESIGN AUTHORITY

Approved documentation SHALL define the intended
institutional design.

Implementation SHALL not silently diverge from
approved documentation.

Where repository state and approved documentation
conflict,
the conflict SHALL be identified and resolved
explicitly.

8. ARCHITECTURE FREEZE

Approved architecture SHALL remain frozen during
implementation unless explicit architecture
authority authorizes change.

Implementation SHALL NOT

reopen approved decisions,

replace approved ownership,

reorder approved execution,

or introduce alternative architecture

merely because another implementation appears
simpler.

9. IMPLEMENTATION AUTHORITY

Implementation authority SHALL define who or what
may

create files,

modify files,

delete files,

change dependencies,

change configuration,

run migrations,

deploy capability,

activate capability,

and certify completion.

Technical access SHALL NOT automatically create
architectural authority.

10. IMPLEMENTATION OWNERSHIP

Every implementation unit SHALL have explicit
ownership.

Ownership SHALL identify responsibility for

design compliance,

code,

integration,

validation,

documentation,

and operational readiness.

Shared implementation SHALL not create ambiguous
responsibility.

Every unit SHALL have a defined boundary.

COREI implementation SHALL preserve the hierarchy

Stage

The exact hierarchy MAY be extended by approved

Hierarchy SHALL remain traceable.

13. STAGE

A Stage represents a major institutional
construction or enablement boundary.

A Stage SHALL define

objective,

scope,

dependencies,

phases,

deliverables,

validation,

and completion criteria.

Stage completion SHALL require evidence.

14. PHASE

A Phase represents a controlled implementation
boundary within a Stage.

A Phase SHALL define

objective,

scope,

ownership,

dependencies,

steps,

deliverables,

validation,

and completion criteria.

15. STEP

A Step represents an executable unit of
implementation progress.

A Step SHOULD be sufficiently bounded to allow

implementation,

validation,

and traceable completion.

Steps SHALL not silently expand scope.

16. SUBSYSTEM

A Subsystem represents a coherent implementation
boundary with explicit responsibility.

Subsystem ownership SHALL preserve

public contracts,

internal implementation,

dependencies,

and lifecycle.

17. IMPLEMENTATION ARTIFACT

Implementation artifacts MAY include

source code,

configuration,

schemas,

manifests,

workflows,

migrations,

tests,

scripts,

documentation,

and generated assets.

Every consequential artifact SHALL have an
appropriate repository location.

18. EXECUTION ORDER

Implementation SHALL follow approved execution
order.

Execution order SHALL be determined by

authority,

dependency,

ownership,

and lifecycle.

Convenience SHALL not override dependency order.

19. DEPENDENCY-FIRST IMPLEMENTATION

A capability SHALL not be implemented as though its
required dependencies already exist when they do
not.

Dependencies SHALL be

identified,

validated,

consumed,

or explicitly scheduled

before dependent capability is certified.

20. FOUNDATION BEFORE CONSUMER

Shared foundational capability SHALL be implemented
before dependent consumers where architecture
requires it.

Consumers SHALL use approved foundation.

Consumers SHALL NOT rebuild foundation locally.

21. CONSUME BEFORE CREATE

Before creating new capability,
implementation SHALL determine whether approved
capability already exists.

Existing approved capability SHALL be

consumed,

integrated,

or extended through authorized contracts

before duplicate capability is created.

22. INTEGRATE BEFORE REBUILD

Completed institutional capability SHALL be
integrated rather than rebuilt.

Reimplementation of completed foundation is
prohibited unless explicit authority requires
replacement.

23. PLATFORM CONSTRUCTION TO PLATFORM ENABLEMENT

When foundational platform construction is
complete,
implementation SHALL transition to platform
enablement.

Platform enablement SHALL

consume,

integrate,

operationalize,

and expose

completed platform capability.

The transition SHALL prevent repeated foundation
construction.

24. EXISTING IMPLEMENTATION INSPECTION

Before modification,
implementation SHALL inspect existing repository
state.

Inspection SHOULD identify

files,

directories,

public APIs,

dependencies,

ownership,

tests,

configuration,

and current behaviour.

Implementation SHALL not assume an empty system.

25. CURRENT STATE CERTIFICATION

Where required,
the current state SHALL be certified before
implementation.

Certification MAY include

repository audit,

directory audit,

ownership audit,

dependency audit,

circular dependency audit,

and implementation-state audit.

Unknown current state creates implementation risk.

26. TARGET STATE

Every implementation unit SHALL define a target
state.

The target state SHALL be derived from approved
authority.

Target state SHALL not be invented during coding
without authorization.

27. GAP IDENTIFICATION

Implementation SHALL identify the gap between

current state

and

approved target state.

Only the required gap SHALL be implemented.

Unrelated redesign SHALL be avoided.

28. CHANGE BOUNDARY

Every implementation step SHALL define its change
boundary.

The boundary SHOULD identify

files to create,

files to modify,

files to remove,

contracts affected,

dependencies affected,

and behaviour affected.

Change boundaries SHALL minimize uncontrolled
scope expansion.

29. FILE OWNERSHIP

Every implementation file SHALL belong to an
appropriate architectural owner.

Files SHALL not be placed according to temporary
convenience.

Repository structure SHALL reflect system
ownership.

30. DIRECTORY OWNERSHIP

Directories SHALL represent coherent ownership
boundaries.

A directory SHALL not become a dumping ground for
unrelated implementation.

31. PUBLIC API

Subsystems SHALL expose explicit public contracts
where required.

Consumers SHOULD depend upon approved public APIs.

Consumers SHALL not unnecessarily depend upon
internal implementation details.

32. INTERNAL IMPLEMENTATION

Internal implementation SHALL remain owned by its
subsystem.

Internal structure MAY evolve without breaking
consumers where public contracts remain stable.

33. DEPENDENCY DIRECTION

Dependencies SHALL follow approved architectural
direction.

Lower-level implementation SHALL not depend upon
higher-level consumers unless explicitly designed.

Dependency inversion SHALL be deliberate.

34. CIRCULAR DEPENDENCIES

Unapproved circular dependencies are prohibited.

Circular dependency checks SHALL be performed where
appropriate.

Detected cycles SHALL be corrected at the ownership
boundary.

35. CONTRACT-FIRST IMPLEMENTATION

Where multiple components interact,
contracts SHOULD be defined before dependent
implementation.

Contracts MAY include

types,

interfaces,

schemas,

events,

APIs,

commands,

queries,

or lifecycle contracts.

36. TYPE SAFETY

Typed implementation SHALL preserve meaningful
domain and platform contracts.

Unsafe type bypass SHALL not become normal
implementation practice.

Type validation SHALL be part of build validation
where applicable.

37. SCHEMA SAFETY

Data and event schemas SHALL be

explicit,

versioned,

validated,

and compatible

according to approved policy.

Schema changes SHALL consider existing consumers.

38. CONFIGURATION

Configuration SHALL be separated from implementation
where appropriate.

Production configuration SHALL be

controlled,

versioned,

validated,

and attributable.

Hidden configuration is prohibited.

39. ENVIRONMENT-SPECIFIC CONFIGURATION

Environment-specific values SHALL not silently
alter architectural behaviour.

Differences between

development,

test,

paper,

staging,

and production

SHALL remain explicit.

40. SECRET HANDLING

Secrets SHALL NOT be embedded in implementation
artifacts.

Secret access SHALL follow approved security and
runtime mechanisms.

41. IMPLEMENTATION DETERMINISM

Implementation processes SHOULD be deterministic
where practical.

Equivalent source,
configuration,
and dependency state

SHOULD produce equivalent build and deployment
outcomes.

42. REPRODUCIBILITY

Critical implementation SHALL be reproducible.

A future authorized engineer or automation system
SHOULD be able to reconstruct the implementation
state from

repository,

dependencies,

configuration,

and documented procedure.

43. SCRIPTED IMPLEMENTATION

Repeatable implementation operations SHOULD be
scripted.

Scripts SHALL be

reviewable,

repeatable,

and versioned

where consequential.

Unrecorded manual mutation SHALL be avoided.

44. NO MANUAL PATCH WORK

COREI implementation SHALL NOT rely upon permanent

manual edits,

one-off server mutation,

untracked console changes,

or undocumented fixes.

Required change SHALL be represented in the
appropriate authoritative artifact.

45. NO HIDDEN IMPLEMENTATION

Production behaviour SHALL not depend upon hidden

local files,

operator memory,

untracked scripts,

or undocumented external state.

Institutional implementation SHALL remain
discoverable.

46. NO DUPLICATE FOUNDATION

A consumer SHALL NOT recreate existing

provider,

capability,

runtime,

state,

event,

workspace,

service,

module,

engine,

or domain foundation

inside its own boundary.

Existing institutional foundation SHALL be
consumed.

47. NO ARCHITECTURE DRIFT

Implementation SHALL not silently create a second
architecture.

Architecture drift SHALL be detected through

repository review,

dependency review,

ownership review,

and validation.

48. NO PREMATURE ABSTRACTION

Implementation SHALL not create abstractions
without clear institutional purpose.

Abstraction SHALL support

ownership,

reuse,

contracts,

or lifecycle.

Complexity without authority is prohibited.

49. NO PREMATURE OPTIMIZATION

Implementation SHALL prioritize

correctness,

determinism,

safety,

and maintainability

before speculative optimization.

Performance optimization SHALL be evidence-driven.

50. NO UNAUTHORIZED SIMPLIFICATION

Institutional requirements SHALL not be removed
because simpler implementation is easier.

Complexity SHALL be reduced only when approved
requirements remain satisfied.

51. NO SCOPE EXPANSION

An implementation step SHALL not silently expand
into unrelated work.

Newly discovered work SHALL be

recorded,

classified,

and scheduled

according to authority.

52. NO TODO AS COMPLETION

A required implementation SHALL not be certified
complete while mandatory behaviour remains only as

TODO,

placeholder,

mock,

stub,

or comment

unless the approved phase explicitly permits it.

53. NO MOCK PRODUCTION AUTHORITY

Mock or simulated capability SHALL not silently
enter production authority.

Simulation boundaries SHALL remain explicit.

54. IMPLEMENTATION MODES

Implementation MAY occur in modes such as

Foundation Construction

Platform Construction

Platform Enablement

Domain Integration

Application Integration

Migration

Hardening

Operationalization

Optimization

Retirement

The active mode SHALL reflect approved project
state.

55. FOUNDATION CONSTRUCTION

Foundation Construction establishes shared
institutional capability.

Foundation SHALL be

generic where intended,

owned,

contract-driven,

and reusable.

Foundation SHALL not absorb domain-specific
authority unnecessarily.

56. PLATFORM CONSTRUCTION

Platform Construction establishes shared runtime
and institutional capability.

Platforms SHALL expose controlled contracts to
consumers.

57. PLATFORM ENABLEMENT

Platform Enablement activates completed platform
capability through

integration,

registration,

composition,

configuration,

and consumption.

Enablement SHALL NOT rebuild completed platform
foundation.

58. DOMAIN IMPLEMENTATION

Domain implementation SHALL express domain-specific
authority and behaviour.

Domains SHALL consume shared platforms.

Domains SHALL not recreate platform ownership.

59. APPLICATION IMPLEMENTATION

Applications SHALL compose approved capability into
operator or user-facing experiences.

Applications SHALL not silently become owners of
platform or domain logic.

60. INFRASTRUCTURE IMPLEMENTATION

Infrastructure implementation SHALL follow approved
infrastructure architecture.

Infrastructure changes SHALL preserve

reproducibility,

security,

observability,

recovery,

and dependency order.

61. DATA IMPLEMENTATION

Data implementation SHALL preserve

authority,

schema,

quality,

lineage,

freshness,

and recoverability.

Data pipelines SHALL not create ambiguous data
ownership.

62. SECURITY IMPLEMENTATION

Security implementation SHALL preserve

identity,

least privilege,

secret protection,

audit,

and recovery.

Security controls SHALL be implemented as
institutional capability,
not decorative configuration.

63. TRADING IMPLEMENTATION

Trading implementation SHALL preserve the
authoritative trading domain chain.

Market intelligence SHALL not bypass

signal,

decision,

risk,

portfolio,

or execution authority.

Financially consequential implementation SHALL
remain bounded by deterministic controls.

64. AUTOMATION IMPLEMENTATION

Automation SHALL implement explicit workflow
authority.

Automation SHALL preserve

input validation,

state,

error handling,

idempotency,

observability,

and recovery

where required.

Automation SHALL not expand its own authority.

65. AI IMPLEMENTATION

Artificial intelligence capability SHALL be
integrated within explicit institutional
boundaries.

AI SHALL NOT silently own

architecture,

risk,

execution,

security,

or irreversible operational authority.

Probabilistic capability SHALL remain bounded by
deterministic control.

66. IMPLEMENTATION WORKFLOW

Every material implementation unit SHOULD follow

Objective

↓

67. OBJECTIVE

Every implementation step SHALL have a clear
objective.

The objective SHALL describe the required outcome.

The objective SHALL not be replaced by a vague list
of activities.

68. CURRENT STATE

Current state SHALL identify what already exists.

Implementation SHALL not duplicate or destroy
existing capability through assumption.

69. TARGET STATE DEFINITION

Target state SHALL identify what shall exist after
implementation.

Target state SHALL be measurable.

70. FILE PLAN

Implementation SHOULD identify exact files to

create,

update,

move,

or remove

before consequential modification.

File planning SHALL support review and scope
control.

71. COMPLETE FILE IMPLEMENTATION

Where a file is created or materially replaced,
implementation SHOULD provide a complete coherent
artifact.

Fragmented patch work SHALL be avoided when a full
authoritative replacement is safer and clearer.

72. FILE NAMING

File names SHALL follow approved repository and
domain conventions.

Names SHALL communicate

ownership,

purpose,

and identity

where applicable.

73. IMPLEMENTATION COMMANDS

Operational implementation commands SHALL be

explicit,

ordered,

and reproducible.

Commands SHALL avoid uncontrolled mutation.

74. COMMAND SAFETY

Destructive commands SHALL be used deliberately.

Before destructive action,
implementation SHALL understand

target,

scope,

recovery,

and impact.

75. MIGRATION

Migration SHALL preserve

state,

compatibility,

authority,

and recoverability.

Migration SHALL define

source,

target,

transition,

validation,

rollback or roll-forward,

and completion.

76. INCREMENTAL IMPLEMENTATION

Large capability SHOULD be implemented through
bounded increments.

Each increment SHALL preserve architectural
direction.

Incremental SHALL not mean structurally incomplete
patch work.

77. ATOMIC IMPLEMENTATION

Where practical,
implementation steps SHOULD create coherent
reviewable units.

A step SHOULD avoid leaving the repository in an
unintentionally broken intermediate state.

78. INTEGRATION

Implementation is incomplete until required
integration is complete.

Integration MAY include

registration,

dependency injection,

routing,

event subscription,

state connection,

runtime composition,

public export,

or application consumption.

79. REGISTRATION

Capabilities requiring registration SHALL be
registered through approved mechanisms.

Registration SHALL not be duplicated across
unrelated owners.

80. COMPOSITION

Composition SHALL connect capability without
collapsing ownership boundaries.

Composition roots SHALL be explicit where required.

81. RUNTIME INTEGRATION

Runtime integration SHALL ensure that implemented
capability can participate in the approved runtime
lifecycle.

Implementation existing only as unused source code
is not operational integration.

82. EVENT INTEGRATION

Event integration SHALL preserve

event identity,

schema,

producer ownership,

consumer ownership,

ordering assumptions,

idempotency,

and failure handling.

83. STATE INTEGRATION

State integration SHALL preserve

state ownership,

lifecycle,

consistency,

persistence,

and recovery.

Shared state SHALL not become ownerless.

84. PROVIDER INTEGRATION

Provider integration SHALL consume approved provider
contracts.

Provider-specific behaviour SHALL remain isolated
within appropriate ownership boundaries.

85. CAPABILITY INTEGRATION

Capabilities SHALL be integrated through approved
capability contracts.

Capability consumers SHALL not depend unnecessarily
upon implementation internals.

86. WORKSPACE INTEGRATION

Workspace implementation SHALL consume approved
workspace foundation and runtime.

Workspaces SHALL not rebuild shared shell,
lifecycle,
or state infrastructure.

87. EXPERIENCE INTEGRATION

Experience implementation SHALL consume approved
experience capability.

Visual and interaction layers SHALL not absorb
domain authority.

88. VALIDATION PRINCIPLE

Implementation SHALL be validated before
completion.

Validation SHALL answer

Does it build?

Does it match architecture?

Does it preserve ownership?

Does it integrate?

Does it behave correctly?

Can it operate safely?

Can it recover?

89. BUILD VALIDATION

Build validation MAY include

type checking,

compilation,

bundling,

linting,

dependency resolution,

and artifact generation.

Build failure SHALL block completion.

90. TYPE VALIDATION

Typed systems SHALL pass required type validation.

Unresolved type errors SHALL not be hidden through
unsafe suppression without explicit justification.

91. REPOSITORY VALIDATION

Repository validation SHALL inspect

folder structure,

file placement,

public API,

ownership,

dependencies,

and prohibited duplication.

Repository correctness is part of implementation
correctness.

92. ARCHITECTURE VALIDATION

Architecture validation SHALL confirm

ownership boundaries,

dependency direction,

layer boundaries,

platform consumption,

and absence of unauthorized redesign.

93. DEPENDENCY VALIDATION

Dependency validation SHALL identify

missing dependencies,

unapproved dependencies,

duplicate dependencies,

and circular dependencies

where applicable.

94. CONTRACT VALIDATION

Contracts SHALL be validated between producers and
consumers.

Contract mismatch SHALL block integration
completion.

95. BEHAVIOURAL VALIDATION

Behavioural validation SHALL verify required
runtime behaviour.

Successful compilation SHALL not prove behavioural
correctness.

96. INTEGRATION VALIDATION

Integration validation SHALL confirm that
implemented capability participates correctly in
the wider system.

Unused or unreachable implementation SHALL not be
certified as integrated.

97. VISUAL VALIDATION

User-facing implementation SHALL receive visual
validation where applicable.

Visual validation MAY include

browser result,

layout,

interaction,

state,

responsive behaviour,

and expected operator experience.

98. OPERATIONAL VALIDATION

Production-relevant capability SHALL validate

health,

observability,

configuration,

failure behaviour,

recovery,

and operational control.

99. SECURITY VALIDATION

Security-relevant implementation SHALL validate

authentication,

authorization,

secret handling,

privilege,

audit,

and failure behaviour.

100. DATA VALIDATION

Data implementation SHALL validate

schema,

quality,

freshness,

lineage,

persistence,

and recovery

where applicable.

101. TRADING VALIDATION

Trading implementation SHALL validate

market data,

signals,

decisions,

risk,

portfolio,

execution,

positions,

reconciliation,

and emergency controls

according to scope.

102. FAILURE VALIDATION

Critical implementation SHALL validate important
failure paths.

Happy-path success SHALL not alone prove production
readiness.

103. RECOVERY VALIDATION

Stateful and critical implementation SHALL validate
recovery where required.

Restartability SHALL not be confused with trusted
recovery.

104. TEST EVIDENCE

Validation SHALL preserve sufficient evidence.

Evidence MAY include

commands,

results,

test output,

build output,

screenshots,

logs,

metrics,

or repository state.

Completion SHALL be evidence-based.

105. IMPLEMENTATION DOCUMENTATION

Implementation documentation SHALL record what was
actually implemented.

Documentation SHALL not describe unimplemented
future behaviour as completed state.

106. DOCUMENTATION SEPARATION

Implementation and documentation SHALL remain
distinct activities.

Implementation creates system capability.

Documentation preserves institutional knowledge.

Both SHALL remain synchronized.

107. IMPLEMENTATION RECORD

A material implementation record SHOULD identify

objective,

scope,

files,

changes,

integration,

validation,

result,

and next step.

The record SHALL support continuity.

108. COMPLETION CRITERIA

An implementation unit SHALL be complete only when

required artifacts exist,

integration is complete,

mandatory validation passes,

documentation is updated,

and unresolved blocking issues are absent.

Code existence alone SHALL not equal completion.

109. PARTIAL COMPLETION

Partially completed implementation SHALL remain
explicitly partial.

Partial SHALL not be represented as complete.

110. BLOCKED STATE

Implementation SHALL be marked blocked when a
required dependency,
authority,
or decision

prevents correct completion.

Blocked work SHALL not be bypassed through patch
work.

111. DEFERRED WORK

Deferred work SHALL be explicit.

Deferral SHALL identify

scope,

reason,

impact,

owner,

and future execution point

where applicable.

112. IMPLEMENTATION DEBT

Implementation debt SHALL remain visible.

Debt MAY include

temporary compatibility,

manual operation,

missing automation,

incomplete tests,

or migration residue.

Debt SHALL not be hidden inside completed status.

113. IMPLEMENTATION EXCEPTION

Implementation exceptions SHALL be governed.

Every exception SHALL define

requirement,

reason,

scope,

risk,

owner,

compensating control,

and expiration

where applicable.

114. CHANGE REVIEW

Material implementation changes SHALL receive
review appropriate to risk.

Review SHOULD examine

architecture,

ownership,

correctness,

security,

operations,

and maintainability.

115. IMPLEMENTATION APPROVAL

Approval SHALL reflect the authority of the change.

Code approval SHALL not automatically equal

architecture approval,

security approval,

risk approval,

or production activation approval.

116. PRODUCTION ACTIVATION

Implementation completion SHALL remain distinct
from production activation.

Activation SHALL require applicable

deployment,

configuration,

readiness,

authority,

and operational controls.

117. FEATURE ENABLEMENT

Implemented capability MAY remain disabled until
explicitly enabled.

Deployment SHALL not automatically create
operational authority.

118. ROLLBACK

Material implementation SHOULD define rollback or
roll-forward strategy where required.

Rollback SHALL consider

state,

schema,

compatibility,

and dependent consumers.

119. DEPRECATION

Deprecated implementation SHALL be explicitly
identified.

Deprecation SHALL define

replacement,

consumer migration,

compatibility period,

and removal criteria.

120. RETIREMENT

Implementation SHALL be retired only after

consumers are migrated,

runtime use is removed,

state is handled,

dependencies are removed,

documentation is updated,

and recovery references are corrected.

121. IMPLEMENTATION CONTINUITY

Implementation knowledge SHALL survive

chat changes,

engineer changes,

tool changes,

model changes,

and technology changes.

Critical project state SHALL be preserved in
authoritative artifacts.

122. CONTINUITY DOCUMENTS

Where implementation spans multiple sessions or
environments,
continuity documentation SHALL preserve

current stage,

current phase,

current step,

completed work,

active constraints,

next execution point,

and authoritative references.

123. SESSION CONTINUITY

A new implementation session SHALL restore context
from authoritative project state.

The session SHALL NOT redesign completed work merely
because prior conversational context is absent.

124. TOOL CONTINUITY

Implementation SHALL not depend upon one specific
assistant,
IDE,
or operator interface

for institutional understanding.

The repository and authoritative documentation
SHALL preserve continuity.

125. IMPLEMENTATION AUTOMATION

Automation MAY support

repository inspection,

file generation,

validation,

testing,

deployment,

and documentation.

Automation SHALL follow the same authority and
architecture boundaries as human implementation.

126. AI-ASSISTED IMPLEMENTATION

Artificial intelligence MAY support implementation.

AI SHALL

inspect current state,

follow approved architecture,

respect repository ownership,

implement bounded scope,

validate output,

and preserve evidence.

AI SHALL NOT assume authority to redesign frozen
architecture.

127. AI CONTEXT DISCIPLINE

AI-assisted implementation SHALL prioritize

authoritative project documents,

repository state,

approved stage documents,

and current implementation evidence.

Generic best practice SHALL not override approved
COREI architecture.

128. AI HALLUCINATION CONTROL

AI SHALL not invent

files,

APIs,

dependencies,

completed capability,

or repository state

without evidence.

Unknown state SHALL be inspected or identified as
unknown.

129. AI CHANGE BOUNDARY

AI implementation SHALL remain within the requested
change boundary.

Unrequested redesign SHALL be prohibited.

130. AI VALIDATION REQUIREMENT

AI-generated implementation SHALL receive the same
validation required for any other implementation.

Generated code SHALL not be trusted solely because
it appears syntactically correct.

131. IMPLEMENTATION RESPONSE STANDARD

Implementation execution communication SHOULD be
concise and action-oriented.

Where appropriate,
the response structure SHOULD prioritize

Objective

Files

Implementation

Validation

Result

Next Step

Detailed architecture discussion SHALL be provided
when required,
not repeated during every implementation step.

132. DOCUMENTATION RESPONSE STANDARD

Documentation work SHALL preserve sufficient
institutional detail.

Documentation MAY include

objective,

purpose,

scope,

architecture,

design decisions,

rationale,

standards,

execution flow,

controls,

validation,

and authority.

Documentation SHALL not be artificially compressed
when completeness is required.

134. TRACEABILITY

Implementation SHOULD be traceable from

constitutional requirement

to

architecture

to

specification

to

implementation

to

validation

to

operation

where applicable.

135. IMPLEMENTATION AUDIT

Material implementation SHALL support audit of

who changed what,

why it changed,

what authority applied,

what validation occurred,

and what became operational.

136. IMPLEMENTATION METRICS

Implementation metrics MAY include

build success,

test success,

validation coverage,

dependency violations,

architecture violations,

deployment success,

rollback rate,

defect rate,

and recovery success.

Metrics SHALL support engineering improvement.

137. IMPLEMENTATION QUALITY

Implementation quality SHALL be evaluated through

correctness,

architecture alignment,

ownership clarity,

determinism,

maintainability,

observability,

security,

and recoverability.

Code volume SHALL not define quality.

138. IMPLEMENTATION SPEED

Speed SHALL be achieved through

clear architecture,

reusable foundations,

automation,

strong contracts,

and deterministic process.

Speed SHALL NOT be achieved through

control bypass,

patch work,

or accumulated hidden debt.

139. IMPLEMENTATION SIMPLICITY

Implementation SHOULD remain as simple as possible
while satisfying institutional requirements.

Simplicity SHALL remove unnecessary complexity.

It SHALL NOT remove necessary controls.

140. IMPLEMENTATION CONSISTENCY

Similar capability SHOULD follow consistent

structure,

contracts,

naming,

validation,

and lifecycle

where architecture permits.

Consistency reduces institutional operating cost.

141. IMPLEMENTATION EVOLUTION

Implementation practice SHALL evolve through

repository evidence,

operational experience,

incident learning,

technology change,

and institutional growth.

Evolution SHALL preserve authority and continuity.

142. RELATIONSHIP TO IDENTITY

Implementation SHALL express COREI institutional
identity.

Implementation decisions SHALL preserve

determinism,

professional control,

institutional scale,

and long-term continuity.

143. RELATIONSHIP TO GOVERNANCE

Governance defines authority and decision rights.

Implementation SHALL execute within those rights.

Technical ability SHALL not override governance.

144. RELATIONSHIP TO ARCHITECTURE

Architecture defines

boundaries,

ownership,

dependencies,

and system shape.

Implementation SHALL realize architecture.

Implementation SHALL not silently replace it.

145. RELATIONSHIP TO ENGINEERING

Engineering defines how capability is constructed
with professional technical discipline.

Implementation applies those engineering
principles to actual system artifacts.

146. RELATIONSHIP TO STANDARDS

Standards define repeatable institutional
requirements.

Implementation SHALL conform to applicable
standards.

147. RELATIONSHIP TO SPECIFICATIONS

Specifications define exact required behaviour and
contracts.

Implementation SHALL realize specifications.

Where implementation reveals specification
ambiguity,
the ambiguity SHALL be resolved explicitly.

148. RELATIONSHIP TO OPERATIONS

Operations defines how implemented capability is
run,
controlled,
observed,
recovered,
and evolved.

Implementation SHALL include operational
requirements before production completion.

152. IMPLEMENTATION VALIDATION QUESTIONS

Every material implementation unit shall answer the
following institutional questions.

What is the objective?

What authority requires it?

What already exists?

What is the approved target state?

Who owns the capability?

What dependencies exist?

What is the approved execution order?

What files will be created?

What files will be modified?

What files will be removed?

What contracts are affected?

Does existing capability already solve this need?

Are we consuming completed foundation?

Are we duplicating platform capability?

Are we changing architecture?

Is that architecture change authorized?

Does dependency direction remain correct?

Are there circular dependencies?

Is the implementation deterministic?

Is configuration controlled?

Are secrets handled correctly?

Is the capability integrated?

Is the capability reachable at runtime?

Does it build?

Does it type-check?

Does it behave correctly?

Does it fail safely?

Is it observable?

Can it recover?

Is documentation synchronized?

Can another authorized engineer continue from the
repository and documentation?

Can the complete implementation decision be
reconstructed?

If any mandatory answer is negative,

implementation readiness or completion remains
incomplete.
